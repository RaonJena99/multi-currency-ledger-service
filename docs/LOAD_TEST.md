# 부하 테스트

거래 API 의 처리량과 지연, 한 계좌에 요청이 몰릴 때의 락 경합, 포트폴리오 캐시의 효과, 분개 기록 지연을
k6 로 측정한 결과입니다. 스크립트는 [`loadtest/`](../loadtest)에 있고 CI 에서는 돌리지 않습니다.

## 요약

| 항목 | 결과 |
| :--- | :--- |
| 거래 API 처리량 (계좌 20개, 경합 없음) | **약 1,250 건/s**, p95 23ms, 실패 0% |
| 한 계좌에 동시 매수 20개 | 성공 약 220 건/s, 11.6% 가 409 `CONCURRENCY_CONFLICT` |
| 포트폴리오 조회 (캐시 적중) | p50 1.8ms, p95 2.4ms |
| 포트폴리오 조회 (입금 직후) | p50 52ms — 캐시 재구성 락을 50ms 폴링으로 기다린다 |
| 분개 기록 지연 (유휴 상태) | p50 0.62s, p95 1.03s (#110 이전 p50 2.2s, p95 4.9s) |
| 아웃박스 릴레이 처리량 | 약 3,200 건/s (#110 이전 약 19 건/s) |
| 원장 기록 컨슈머 처리량 | 약 1,200 건/s |

처음 측정에서 가장 중요한 발견은 아웃박스 릴레이였습니다. 잔고는 초당 1,250 건씩 바뀌는데 분개는 초당 약 19 건씩만
기록되었습니다. #110 에서 고친 뒤에는 거래 속도를 따라가며, 다음 상한은 원장 기록 컨슈머(약 1,200 건/s)입니다.
[아래](#1-아웃박스-릴레이가-분개-기록의-상한이다)에 원인, 영향, 개선 결과를 적었습니다.

## 환경

모든 구성 요소가 노트북 한 대에서 돕니다. 절대값보다 시나리오 사이의 비교와 병목의 위치에 의미가 있습니다.

| 항목 | 값 |
| :--- | :--- |
| 호스트 | Intel Core Ultra 9 185H, RAM 64GB, Windows 11 |
| Docker | Docker Desktop 29.7 (WSL2), 할당 22 CPU / 31GB |
| 스택 | `deploy/docker-compose.yml` 그대로 (앱 1대, PostgreSQL 15, Redis 7, Kafka 3.8 1 브로커) |
| 앱 설정 | `dev` 프로필(더미 시세 1 BTC = 100,000,000 KRW), Hikari 풀 20, 원장 기록 컨슈머 3개 |
| 부하 발생기 | `grafana/k6` 컨테이너, 앱과 같은 Docker 네트워크 |
| 측정일 | 2026-10-07, 커밋 `319c371`. 릴레이 관련 수치는 #110 적용 후 다시 쟀다 |

`local` 프로필은 SQL 과 바인딩 값을 로그로 남겨 측정을 왜곡하므로 쓰지 않습니다.

## 실행 방법

```bash
docker build -t ledger:local .

# 필수 값은 up 과 down 모두에 필요하다. 운영 스택과 겹치지 않게 프로젝트 이름과 앱 포트를 따로 둔다.
export APP_IMAGE=ledger:local DB_PASSWORD=loadtest GATEWAY_SHARED_SECRET=loadtest \
       GRAFANA_ADMIN_PASSWORD=loadtest APP_PORT=18080
COMPOSE="docker compose -f deploy/docker-compose.yml -f loadtest/compose.loadtest.yml -p ledger-loadtest"
$COMPOSE up -d --wait app

# 시나리오 하나 실행 (throughput / contention / portfolio / ledger-lag)
docker run --rm --network ledger-loadtest_default -v "$PWD/loadtest:/scripts" \
  -e GATEWAY_SECRET=loadtest grafana/k6 run /scripts/throughput.js

$COMPOSE down -v   # 정리
```

- Git Bash 에서는 경로 변환을 막기 위해 `MSYS_NO_PATHCONV=1` 을 붙이고 `$PWD` 대신 `$(pwd -W)` 를 씁니다.
- 동시 사용자 수와 시간은 `-e VUS=… -e DURATION=…` 로 바꿉니다.
- `ledger-lag.js` 는 아웃박스가 밀려 있으면 그 대기 시간까지 잽니다. 다른 시나리오 뒤에 돌릴 때는 `down -v` 로
  스택을 새로 띄웁니다.
- JIT 워밍업을 위해 본 측정 전에 `-e VUS=2 -e DURATION=5s` 로 한 번 짧게 돌렸습니다.

## 시나리오와 결과

### 1. 처리량 — `throughput.js`

VU 20개가 각자 다른 계좌에서 0.0001 BTC 매수·매도를 쉬지 않고 반복합니다(60초). 계좌가 겹치지 않으므로
낙관적 락 충돌이 없는, 거래 API 자체의 기준선입니다.

| 지표 | 값 |
| :--- | :--- |
| 처리량 | 1,249 req/s (매수 37,662 건 + 매도 37,662 건) |
| 지연 | avg 15.7ms, p50 14.6ms, p95 23.3ms, p99 32.9ms, max 599ms |
| 실패율 | 0% |

최대값 599ms 는 시작 직후 한 번입니다. p99 까지는 35ms 안에 들어옵니다.

#110 적용 후 같은 시나리오는 1,018 req/s, p95 30.5ms 였습니다. 예전에는 릴레이가 거의 쉬고 있었고, 지금은
같은 시간에 아웃박스를 거래 속도로 발행하느라 DB·CPU 를 나눠 쓰기 때문입니다. 실패는 여전히 0% 입니다.

### 2. 락 경합 — `contention.js`

한 계좌에 매수를 동시에 몰아넣습니다(30초). 같은 원장 행을 고치므로 `@Version` 충돌이 나고, 서비스는
100ms → 200ms 백오프로 최대 3회 시도한 뒤 409 를 돌려줍니다.

| VU | 성공 | 409 충돌 | 충돌 비율 | 성공 지연 p50 / p95 | 충돌 지연 p50 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 5 | 196 건/s | 3.6 건/s | 1.8% | 5.3ms / 109ms | 312ms |
| 20 | 221 건/s | 28.9 건/s | 11.6% | 6.4ms / 313ms | 313ms |

- 한 계좌의 처리량은 **초당 약 200 건에서 포화**됩니다. VU 를 4배로 늘려도 성공은 13% 늘고 충돌은 8배가 됩니다.
- 성공 지연이 두 갈래로 나뉩니다. 첫 시도에 성공하면 5ms 안팎, 재시도 끝에 성공하면 100ms·300ms 입니다.
- 충돌 응답은 모두 약 312ms 로, 백오프 합계(100 + 200ms)를 다 쓰고 실패한 것입니다.
- 409 외의 실패(5xx 등)는 없었습니다. 정상 사용자 한 명이 이 정도로 몰아치는 일은 드물지만, 봇·자동매매가
  한 계좌에 붙으면 409 를 재시도할 수 있게 클라이언트가 준비해야 합니다.

### 3. 포트폴리오 조회 — `portfolio.js`

VU 10개가 30초 동안 같은 계좌를 반복 조회한 뒤(캐시 적중), 다시 30초 동안 VU 마다 자기 계좌에 입금하고
곧바로 조회합니다(입금 커밋이 캐시를 지운 직후).

| 경우 | p50 | p95 | p99 |
| :--- | :--- | :--- | :--- |
| 캐시 적중 | 1.75ms | 2.43ms | 3.3ms |
| 입금 직후 | 52.4ms | 53.5ms | 102ms |

입금 직후 조회가 거의 정확히 50ms 인 이유는 캐시 재구성 락입니다. 입금이 커밋되면 비동기 갱신
(`PortfolioViewRefresher`)이 `lock:portfolio:{id}` 를 잡고 캐시를 다시 채웁니다. 그 사이 들어온 조회는 캐시가
비어 있어 같은 락을 시도하고, 실패하면 `LOCK_POLL_MILLIS`(50ms)만큼 잔 뒤 다시 확인합니다. 재구성 자체는
몇 ms 면 끝나므로, 지연의 대부분은 폴링 간격입니다. p99 102ms 는 두 번 기다린 경우로 보입니다.

### 4. 분개 기록 지연 — `ledger-lag.js`

매수 응답을 받은 시점부터 그 거래의 분개 상세(`GET /accounts/{id}/transactions/{tradeId}`)가 200 을 돌려줄
때까지를 200ms 간격으로 폴링해 잽니다. VU 5개 × 20회, 스택을 새로 띄운 유휴 상태입니다.

| 지표 | #110 이전 (5초 폴링) | #110 이후 (1초 폴링) |
| :--- | :--- | :--- |
| 지연 | avg 2.46s, p50 2.23s, p95 4.89s, max 5.10s | avg 0.64s, p50 0.62s, p95 1.03s, max 1.05s |
| 30초 안에 기록되지 않은 거래 | 0 | 0 |

지연이 폴링 주기 안에 고르게 퍼지는 것은 아웃박스 릴레이의 폴링(`ledger.outbox.relay.poll-interval-ms`) 때문입니다.
Kafka 와 컨슈머가 더하는 시간은 100ms 남짓이고, 측정 스크립트의 조회 간격(200ms)만큼 오차가 있습니다. 처음에는 매수 직후 바로 다음 매수를 보내 지연이 늘 5초 가까이
나왔습니다. 매수 시각이 릴레이 실행 직후에 고정되었기 때문이라, 매수 전에 0~5초를 무작위로 쉬게 바꿨습니다.

## 발견한 병목

### 1. 아웃박스 릴레이가 분개 기록의 상한이다

해결: [#110](https://github.com/RaonJena99/multi-currency-ledger-service/issues/110) ([개선 결과](#110-적용-후))

`OutboxRelayWorker` 는 5초마다 최대 100 건을 가져와 발행합니다. 이론상 상한은 초당 20 건이고, 실측은
32초 동안 600 건(약 19 건/s)이었습니다.

처리량 시나리오 60초 동안 아웃박스 이벤트가 약 76,000 건 쌓였고, 끝난 시점에 처리된 것은 1,700 건이었습니다.
남은 74,000 건을 비우는 데 **약 65분**이 걸립니다. 그동안 생기는 일은 다음과 같습니다.

- 잔고·포트폴리오는 즉시 맞지만, 거래 내역·분개 상세는 최대 한 시간 가까이 보이지 않습니다(404).
- 정합성 점검은 "아웃박스가 남은 계좌"를 건너뛰므로 점검 범위가 그만큼 줄어듭니다.
- 노드를 늘리면 `SKIP LOCKED` 덕분에 노드 수만큼 빨라지지만, 노드당 20 건/s 라는 구조는 그대로입니다.

지속 가능한 거래량은 현재 설정에서 **초당 약 19 건**입니다. 거래 API 가 이보다 빠르게 받으면 그 차이만큼
아웃박스가 계속 쌓입니다. 배치 크기와 주기를 설정으로 빼고, 가져온 배치가 꽉 찼으면 쉬지 않고 다음 배치를
가져오게 바꾸는 것이 가장 효과가 큽니다.

#### #110 적용 후

- 배치 크기(기본 500), 실행당 최대 배치 수(기본 20), 폴링 주기(기본 1초)를 `ledger.outbox.relay.*` 로 뺐습니다.
- 배치가 꽉 찼고 실패가 없으면 다음 주기를 기다리지 않고 이어서 가져옵니다.
- 발행 대기 건수(`outbox_backlog`)와 가장 오래된 대기 이벤트의 나이(`outbox_oldest_pending_age_seconds`)를 지표로
  내고, 나이가 5분을 넘은 채로 5분 지속되면 `OutboxBacklogStalled` 경보가 울립니다.

| 측정 | 결과 |
| :--- | :--- |
| 처리량 시나리오(60초, 1,018 req/s) 동안 대기 건수 | 5초마다 샘플링한 최대 약 1,400 건. 부하가 끝나자 곧 0 |
| 릴레이를 멈춰 쌓은 29,142 건을 비우는 시간 | 약 9초 (평균 약 3,200 건/s, 1초 단위 최대 6,500 건) |
| 같은 이벤트를 원장 기록 컨슈머(3개)가 분개로 남기는 속도 | 약 1,200 건/s |

릴레이 한 번 실행이 최대 10,000 건(500 × 20)을 발행하고 1초 쉬므로 처리량은 이 두 값으로 조절합니다. 지금은
원장 기록 컨슈머가 더 느리지만 거래 API 속도(약 1,000 건/s)보다 빠르므로, 이 환경에서 분개가 계속 밀리지는
않습니다. 거래량이 더 늘면 Kafka 파티션과 컨슈머 수(`ledger.kafka.ledger-recording.*`)를 함께 늘립니다.

### 2. 한 계좌의 처리량은 초당 약 200 건에서 포화된다

후속 작업: [#111](https://github.com/RaonJena99/multi-currency-ledger-service/issues/111)

낙관적 락이라 충돌을 재시도로 흡수하지만, 동시 요청이 늘수록 재시도가 부하를 더합니다. 지금 수준이면
개인 계좌에는 충분합니다. 한 계좌에 거래가 집중되는 용도(예: 마켓메이커 계좌)가 생기면 그 계좌의 거래를
직렬화하는 큐나 비관적 락을 검토할 만합니다.

### 3. 쓰기 직후 포트폴리오 조회가 50ms 를 기다린다

후속 작업: [#112](https://github.com/RaonJena99/multi-currency-ledger-service/issues/112)

거래 직후 잔고를 보는 흐름은 흔하므로 체감 지연에 직접 드러납니다. 락 대기 간격을 줄이거나, 대기 중에
캐시가 채워졌는지 먼저 확인하면 수 ms 로 줄일 수 있습니다.

## 측정하지 않은 것

- 여러 앱 노드, 별도 호스트의 DB·Kafka. 모두 한 머신에서 돌았으므로 네트워크 지연이 거의 없습니다.
- 실제 시세 API. 더미 시세라 외부 호출 지연과 서킷 브레이커 동작은 결과에 없습니다.
- 장시간(수 시간) 부하에서의 메모리·커넥션 추이.
